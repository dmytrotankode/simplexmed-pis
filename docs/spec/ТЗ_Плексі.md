## 1. Мета, контекст, межі

### 1.1. Мета

1. Надати пацієнту кабінет, у якому він без посередників бачить і змінює власні відомості в ЕСОЗ: запис про особу, статуси верифікації, методи автентифікації, декларації з лікарем первинної допомоги, доступи сторонніх застосунків.
2. Пройти функціональне тестування НСЗУ та отримати статус кваліфікованої ПІС за ТВ № 978.
3. Дати пацієнту єдину точку доступу до його медичних записів із медичних інформаційних систем закладів (етап Е2 і далі) без порушення принципів ЕСОЗ: ЕСОЗ — джерело юридичних статусів, МІС закладу — джерело клінічних подробиць.
4. Забезпечити три категорії клієнтів на одному сервері: https-веб, мобільний застосунок Android (цільово також iOS і Huawei), адмін-портал співробітників.

### 1.4. Поза обсягом

| Що | Причина |
|---|---|
| Пункти ТВ 3.2 і 3.4 та підпункти, адресовані лише АПІС (зокрема 1.7.1, 3.10.1.2.1) | «Плексі» — КПІС; авторизація через портал електронних послуг (Дія) не застосовується |
| Створення клінічних записів у ЕСОЗ (епізоди, рецепти, направлення, висновки) | Це функція МІС закладу. Кабінет показує статуси й результати та передає запити пацієнта |
| Медична інформація як порада чи діагностика | Продукт не надає медичних послуг |
| Реклама лікарських засобів, брендів, акцій у даних про здоров'я | Правило продукту |
| Пацієнтські дані дітей до 14 років у самостійному кабінеті | Обмеження ТВ 3.5.4 (вік від 14). Профілі дітей — через законного представника, етап Е4 |

### 1.5. Принципи продукту

1. **Токени ЕСОЗ не залишають сервер.** На пристрої користувача — лише токен сесії кабінету.
2. **Ключ КЕП і пароль не залишають пристрій.** Підпис створюється в браузері чи WebView користувача.
3. **Жодних проміжних інтерфейсів авторизації**, крім Сервісу авторизації ЕСОЗ (ТВ 1.5.2).
4. **Дані ЕСОЗ не викривляються** (ТВ 1.2): коди довідників замінюються описом, форми ЕСОЗ показуються як отримані.
5. **Помилки — за Додатком 1.** Таблиця помилок — конфігурація (JSON), а не код.
6. **Збій ЕСОЗ або джерельної МІС не ламає кабінет**: показується зрозумілий текст і наступна дія.
7. **Мінімум даних.** Дані з ЕСОЗ показуються на запит і не зберігаються; кеш джерельної МІС — лише за окремою згодою.
8. **Спокійний інтерфейс.** Одна головна дія на екран, без реклами й емодзі, темна тема рівноправна світлій.

### 1.6. Припущення й обмеження

| № | Припущення |
|---|---|
| П-1 | ЕСОЗ у ТВ ПІС № 978 не передає клінічних записів. Медична картка в кабінеті будується з джерельних МІС (розд. 7), доки ДП ЕЗ не відкриє відповідні скоупи |
| П-2 | Сертифікат відповідності та промислові ключі ЕСОЗ видаються за підсумками тестування НСЗУ |
| П-3 | Терміни створення комплексної системи захисту інформації та її експертизи визначаються за законодавством і не входять у цей документ; статус — у відкритих питаннях (розд. 18) |
| П-4 | Хостинг серверної частини — в Україні або в ЄС; остаточне рішення залежить від відповіді юриста (розд. 18, OQ-3) |

КЛІЄНТИ                       «ПЛЕКСІ» (наш сервер)                    ЗОВНІШНІ СИСТЕМИ

+---------------------+       +-----------------------------------+
| Веб (https)         |       | nginx (TLS 1.2/1.3, заголовки)    |

+---------------------+       |   - валідація форм                |-- читання, події -----> Джерельна МІС

### 2.2. Компоненти

| Компонент | Технологія | Відповідальність |
|---|---|---|
| Веб-клієнт | Одна HTML-сторінка, власний JS, локально зібрані стилі, бібліотека ІІТ EUSign для КЕП | Інтерфейс, підпис на пристрої, запити лише до `/api/*` |
| Мобільний клієнт | Expo / React Native, TypeScript, `expo-router`, `expo-secure-store`, `expo-local-authentication` | Інтерфейс, PIN і біометрія, підпис у WebView з тим самим `kep.js` |
| BFF | Python, Flask, gunicorn, пакет `ehealth_pis` | Усі виклики ЕСОЗ, токени, помилки, кеші |
| Сховище | PostgreSQL; SQLite-кеш реєстрів (до переходу на PostgreSQL) | Користувачі, сесії, доступи, аудит; реєстри |
| Проксі ЦСК | `/api/kep/proxy`, `ca_proxy.py` | Пересилання OCSP / TSP / CMP лише до хостів з `CAs.json` |
| Нормалізатор помилок | `ehealth_pis/errors.py`, `annex1_errors.json` | Текст і дія ПІС за Додатком 1 |

### 2.3. Основні архітектурні рішення

| ID | Рішення |
|---|---|
| AR-01 | Клієнти звертаються лише до BFF; прямих викликів ЕСОЗ з пристрою немає |
| AR-02 | Токени ЕСОЗ (access, refresh) зберігаються лише на BFF у зашифрованому вигляді (Fernet; ключ — у змінних середовища, не в коді), прив'язані до сесії |
| AR-03 | Токен сесії кабінету — випадковий; на сервері зберігається хеш; у веб — cookie `HttpOnly; Secure; SameSite=Strict`; у Android — Keystore (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`) |
| AR-04 | Android входить через Custom Tabs з PKCE; код ЕСОЗ не потрапляє в застосунок — застосунок отримує одноразовий код обміну |
| AR-05 | Таймаут синхронних викликів ЕСОЗ — не менше 60 с (ТВ 1.3.2) |
| AR-06 | Довідники й реєстри кешуються на BFF: не частіше ніж раз на 4 год і не рідше ніж раз на добу (ТВ 3.12) |
| AR-07 | Кожен рядок Додатка 1 — запис у JSON, що генерується з офіційного файла скриптом `tools/build_annex1.py`; тест перевіряє, що JSON актуальний |
| AR-08 | Дані джерельної МІС потрапляють у кабінет лише через модуль-адаптер з канонічною моделлю (розд. 7); ядро BFF не містить логіки конкретної МІС |
| AR-09 | Секрети (API-key ЕСОЗ, ключ шифрування, ключі HMAC МІС) — лише в змінних середовища або захищеному файлі; у репозиторії й журналах їх немає |
| AR-10 | Усі зміни схеми БД — міграції, сумісні назад; видалення колонок у два кроки |

### 2.4. Розгортання

| Параметр | Значення |
|---|---|
| Фронт-проксі | nginx; TLS 1.2 і 1.3; сертифікат ECC P-256/P-384 або RSA ≥ 2048; HSTS |
| BFF | `gunicorn`, слухає `127.0.0.1:3122`, `timeout = 120`; керування `systemd` або `pm2` (`pis/deploy`) |
| Середовища | `dev` (локально), `preprod` (`my-dev.simplex-med.com`, ЕСОЗ PreProd), `prod` (`my.simplex-med.com`) |
| Секрети | змінні середовища: `PIS_CLIENT_SECRET`, `PIS_REDIRECT_URI`, ключ шифрування токенів, параметри БД |
| Збірка Android | EAS Build або локальна збірка (`build-android.sh`); профілі `development`, `preview`, `production` |
| Резервне копіювання | PostgreSQL: щоденні копії, шифровані; контрольне відновлення щоквартально (NFR-16) |

### 2.5. Відмовостійкість

- Збій ЕСОЗ (5xx, мережа, таймаут): відповідь BFF `503` з текстом за Додатком 1 або загальним текстом «Сталася помилка. Зверніться до технічної підтримки» і контактами; кабінет залишається працездатним.
- Збій оновлення access token: токени ЕСОЗ скидаються, сесія кабінету зберігається, користувачу пропонується повторна авторизація в ЕСОЗ.
- Збій джерельної МІС: показуються останні знімки з позначкою свіжості (розд. 7.8).
- Результат змінювальної операції невідомий (таймаут після відправлення): повторна відправлення без звірки заборонено; клієнт показує «статус невідомий» і пропонує оновити перелік.

### 5.3. Обробка помилок (Додаток 1)

1. Кожен виклик ЕСОЗ, що завершився помилкою, проходить через `Annex1.resolve(method, status, error_text)`.
2. Результат: `error` (текст для користувача), `action` (дія ПІС: `Logout`, «перейти до зміни даних», «перейти до реєстрації», нічого), `next_step` (підказка клієнту).
3. Для невідомої помилки — загальний текст «Сталася помилка. Зверніться до технічної підтримки» і контакти підтримки (`PIS_SUPPORT_CONTACTS`).
4. 401 від ЕСОЗ: одна спроба оновлення токена; якщо невдала — очищення токенів ЕСОЗ і пропозиція повторної авторизації.
5. HTML-відповідь зі статусом 200 (сторінка блокування) вважається помилкою.
6. Мережева помилка: `503` із контактами підтримки.

## 7. Інтеграція з джерельною МІС

### 7.1. Призначення

Джерельна МІС — система закладу, що веде клінічні записи пацієнта. Кабінет не прив'язаний до однієї МІС: взаємодія відбувається через канонічний інтерфейс (розд. 7.3), а специфіка конкретної системи — в драйвері.

| Драйвер | Система | Етап | Примітка |
|---|---|---|---|
| `simplexmed` | МІС SimplexMed 2.0 | Е2 | Перша інтеграція |
| `accuracy` | Accuracy 3.0.1 | Е3 | Склад можливостей визначається за результатами обстеження |
| `generic-fhir` | Будь-яка МІС із FHIR-інтерфейсом | Е4 | За потреби |
| `manual` | Заклад без МІС | Е4 | Розклад веде адміністратор закладу в адмін-порталі |

Правило: у ядрі BFF немає гілок «під конкретну МІС». Різниці виражаються набором можливостей (capabilities) і мапінгом полів у драйвері.

### 7.2. Режими

| Режим | Суть | Етап |
|---|---|---|
| Читання (pull) | Кабінет читає списки й деталі за запитом і за подіями | Е2 |
| Події (push + cursor) | МІС надсилає події змін, кабінет також забирає стрічку за курсором | Е2 |
| Дії | Створення й скасування запису, утримання слота | Е3 |

### 7.3. Канонічний інтерфейс джерельної МІС

Усі виклики між серверами — лише по TLS з автентифікацією сервер-сервер (HMAC-підпис тіла й часу або mTLS) і allowlist організацій. Формат — JSON, помилки RFC 9457.

| Операція | Призначення |
|---|---|
| `capabilities` | Версія інтерфейсу, ввімкнені розділи (візити, рецепти, направлення, документи, результати, щеплення, лікарняні, декларації, слоти, дії), режим чутливих записів |
| `match` | Пошук картки за телефоном, датою народження, прізвищем; відповідь — ідентифікатор і маскована назва лише за єдиного збігу |
| `link` / `unlink` | Створення і відкликання зв'язку профілю з карткою з доказом (код підтвердження) |
| `list(kind)` | Список записів з курсором, фільтрами за датою |
| `get(kind, id)` | Деталі запису |
| `document(id, format)` | Вміст документа потоком (PDF або HTML) |
| `events(cursor, limit)` | Стрічка змін; простроченій курсор повертає `410 cursor_expired` |
| `snapshot(kind)` | Повне довантаження |
| `slots(provider, from, to)` | Вільні слоти (Е3) |
| `hold`, `release`, `create`, `cancel` | Дії над записом (Е3) |

### 7.4. Канонічні сутності

Повний перелік полів — у додатку B. Скорочено:

| Сутність | Призначення | Авторитетне джерело |
|---|---|---|
| Patient | Демографія для звірки | МІС (мінімум), ЕСОЗ (особа) |
| Organization, Division | Заклад і місце надання послуг | Реєстри ЕСОЗ, МІС |
| Practitioner | Лікар, фото, спеціальність | Реєстри ЕСОЗ, МІС |
| Service | Послуга, ціна, тривалість | МІС |
| Slot, Appointment | Розклад і запис | МІС |
| Encounter | Завершений візит | МІС |
| Diagnosis | Діагноз візиту (МКХ-10, ICPC-2) | МІС; статус «внесено помилково» — ЕСОЗ |
| ServiceRequest | Е-направлення | Статус — ЕСОЗ; послуга й коментар лікаря — МІС |
| MedicationRequest | Е-рецепт | Статус і погашення — ЕСОЗ; препарат і доза — МІС |
| DiagnosticReport | Результати досліджень | МІС |
| Document | Висновок, виписка, файл | МІС |
| Immunization | Щеплення | МІС, ЕСОЗ |
| SickLeave | Лікарняний | МІС |
| Declaration | Декларація (читання) | ЕСОЗ |

### 7.5. Події

| Подія | Коли | Реакція кабінету |
|---|---|---|
| `entity.changed(kind, id)` | Створено або змінено запис | Точкове читання ≤ 60 с |
| `entity.withdrawn(kind, id)` | Запис анульовано | Прибрати з уявлення, очистити вміст ≤ 24 год |
| `appointment.created / updated / cancelled` | Зміни запису | Оновити «Мої записи», сповістити |
| `slot.changed(provider)` | Зміна розкладу | Оновити кеш слотів |
| `link.revoked` | Зв'язок розірвано в МІС | Знищити знімки джерела для профілю |
| `result.ready` | Результат готовий | Сповістити без змісту |

Подія надходить у двох каналах: push (HMAC) і pull за курсором; дублікати відкидаються за `(source, kind, id, version)`.

### 7.6. Зіставлення і пріоритети

1. Рівень 1: збіг ідентифікатора ЕСОЗ (UUID) — злиття.
2. Рівень 2: збіг бізнес-номера (номер рецепта, направлення, декларації) — злиття.
3. Рівень 3: евристика за типом, датою, закладом, лікарем, кодом; ≥ 0,85 — злиття з позначкою «зіставлено за ознаками»; 0,6–0,85 — не зливати, показати підпис «Схожий запис з іншого джерела»; нижче — незалежні записи.
4. ПІБ і дата народження не є ключем зіставлення записів (лише картки).
5. Правила пріоритету полів:
   - юридичні статуси (декларація, статус рецепта, статус направлення) — ЕСОЗ;
   - клінічні подробиці візиту, діагнози, висновки — МІС;
   - «останній виграє» дозволено лише для назв, адрес, телефонів;
   - поле без явного правила — не зливати: показати значення авторитетного джерела і позначку «Розбіжність».
6. Розбіжності не приховуються і не перезаписуються; вони зберігаються як знімки.

| Статус | Умова |
|---|---|
| «Актуально» | Авторитетні для відображених полів джерела оновлені не раніше TTL виду |
| «Може бути застарілим» | Дані є, але авторитетне джерело не оновлювалося довше TTL або остання спроба невдала (показується час останнього успіху) |

### 7.9. Видалення і згоди

- Відкликання згоди на обробку даних про стан здоров'я: читання зупиняється негайно, шифрований кеш знищується (ключі) протягом 30 днів.
- Видалення облікового запису: знищення профілів, знімків, пристроїв; рядки аудиту й журнал згод знеособлюються.
- Скасування зв'язку з МІС: події `link.revoked` і `DELETE /link`.

### 10.3. Правила

- Первинні ключі — UUID; час — UTC, `timestamptz`.
- Журнали аудиту й подій — додавання без зміни.
- Секрети в таблицях не зберігаються; зберігається посилання на сховище або шифрований вміст.
- Видалення облікового запису — каскадне, за винятком знеособлених рядків аудиту й згод.

## 11. Інтерфейс BFF

### 11.1. Загальні правила

| Правило | Значення |
|---|---|
| Базовий шлях | `/api/…` (клієнти), `/admin/v1/…` (адмін-портал), `/api/source/…` (прийом подій МІС, лише сервер-сервер) |
| Формат | JSON, UTF-8; помилки — `{error, action, next_step, code}`; для нових маршрутів — RFC 9457 |
| Автентифікація клієнтів | cookie сесії (веб) або `Authorization: Bearer <токен сесії>` (мобільний) |
| Автентифікація МІС | HMAC-підпис тіла й часу; вікно 300 с |
| Ідемпотентність | `Idempotency-Key` на створення запису, hold, запит декларації |
| Пагінація | курсорна (`cursor`, `limit` ≤ 100) |
| Обмеження частоти | Політики за групами; 429 з `Retry-After` |
| Невідомий шлях `/api/*` | 404 JSON, не HTML |

### 11.2. Групи (повний перелік наявних — додаток A)

| Група | Маршрути |
|---|---|
| Службові | `/health`, `/api/config`, `/api/privacy-policy` |
| Автентифікація | `/api/auth/*`, `/api/auth-url` |
| Обліковий запис | `/api/account`, `/api/patient/me` |
| ЕСОЗ | `/api/ehealth/*` |
| Реєстри | `/api/registry/*` |
| КЕП | `/api/kep/proxy` |
| Згоди (Е1) | `/api/consents`, `/api/consents/<type>/accept`, `/api/consents/<type>/revoke`, `/api/legal/<type>` |
| Дані МІС (Е2) | `/api/record/timeline`, `/api/record/<kind>/<id>`, `/api/record/<kind>/<id>/sources`, `/api/record/sync-status`, `/api/record/refresh`, `/api/link/*` |
| Запис (Е3) | `/api/booking/*` |
| Тестування (Е1) | `/api/me/tester/*` (404 за відсутності права) |
| Адмін (Е1) | `/admin/v1/*` |

### 11.3. Коди помилок (нові маршрути)

`validation_failed` (422), `unauthenticated` (401), `forbidden` (403), `not_found` (404), `conflict` (409), `slot_unavailable` (409), `consent_required` (403), `cursor_expired` (410), `rate_limited` (429), `ehealth_unavailable` (503), `source_unavailable` (503), `outcome_unknown` (202 з позначкою). Тексти — українською, стабільні `code`.

### 16.2. Критерії приймання (вибірково)

| ID | Сценарій |
|---|---|
| AC-01 | **Given** користувач на екрані входу без згоди **When** натискає «Увійти з КЕП» **Then** авторизація не починається, показується повідомлення про необхідність ознайомитися з Політикою |
| AC-02 | **Given** валідний ключ КЕП **When** пройдено nonce, підпис і Сервіс авторизації **Then** BFF обмінює код на токени, браузер отримує лише cookie сесії, токени ЕСОЗ у відповідях відсутні |

## Додаток B. Сутності й події джерельної МІС (скорочено)

### B.1. Загальний блок запису

| Поле | Опис |
|---|---|
| `id` | Ідентифікатор у МІС |
| `kind` | `encounter`, `diagnosis`, `service_request`, `medication_request`, `diagnostic_report`, `document`, `immunization`, `sick_leave`, `declaration`, `appointment` |
| `externalIds` | `[{system, type, value}]`, зокрема `system = ehealth` |
| `status` | `{code, changedAt}` |
| `visibility` | `patient` або `hidden` |
| `finalized` | Запис завершено й підписано |
| `version` | Хеш видимого уявлення |
| `modifiedAt` | Час зміни в МІС |
| `sync` | Статус передачі в ЕСОЗ: `{system, status, syncedAt, complete}` |

### B.2. Поля за видом (для відображення пацієнту)

| Вид | Дозволені поля |
|---|---|
| encounter | час, лікар, відділення, послуга, висновок, рекомендації |
| diagnosis | код (МКХ-10, ICPC-2), назва, тип, дата |
| service_request | номер, штрихкод, послуга, категорія, пріоритет, строк, статус, виконавець |
| medication_request | номер, МНН, доза, форма, кількість, строк, статус, програма, штрихкод |
| diagnostic_report | категорія, послуга, дати, виконавець, висновок, спостереження (значення, одиниця, референс, ознака) |
| document | назва, дата, тип, вміст (PDF або HTML) |
| immunization | вакцина, дата, доза, серія, виконано або відмова |
| sick_leave | номер, період, лікар |
| declaration | номер, статус, дата підписання, період, лікар, підрозділ, організація |
| appointment | час, лікар, відділення, послуга, статус |

### B.3. Заборонено передавати

Причини скасування й відмов; внутрішні коментарі й примітки колег; службові ціни, коди страхових, ознаки оплати; чернетки; дані інших пацієнтів; ІПН, ВПО, пільги, дані батьків, екстрені контакти (поза межами власного запису ЕСОЗ); технічні маркери, поля аудиту МІС.
